# Правила API Space

У Space отдельный [контракт](index.md) и отдельный origin. Для интеграций передавайте `Authorization: Bearer <space-key>` из [`PUBLIC_API_KEYS` Space](../space.md#access). Веб-интерфейс использует [свою сессию и CSRF](../../space/access.md).

## Расписание и контекст {#execution}

Cron следует местному времени в указанном часовом поясе. При переходе на летнее время отсутствующий момент пропускается, повторяющийся встречается дважды. После простоя рассматривается только последнее актуальное срабатывание.

Если предыдущий запуск подтверждён как активный, очередное срабатывание получает `state=skipped`, `error_code=previous_run_active`. Оно не ждёт своей очереди. Если исход отправки неизвестен или синхронизация статуса не удалась, планирование ждёт восстановления. Периоды, пришедшиеся на фактическое выполнение предыдущего запуска, пропускаются и после его завершения.

При `session_mode=reuse` действуют правила:

| Изменение | Контекст следующего запуска |
| --- | --- |
| Поручение, название, владелец, cron или часовой пояс | Сохраняется |
| Профиль, шаблон, модель, имена ENV, режим сессии, эффективная базовая конфигурация | Новая сессия |
| Явный сброс контекста | Новая сессия. При активном срабатывании — `409 schedule_busy` |

Старые сессии остаются в Orpheus. Их namespace — `schedule`.

## Создание и изменения

Обязательные [поля создания](schema-createschedule.md): `name`, `prompt`, `cron`, `timezone`. По умолчанию `status=active`, `session_mode=new`, `model=null`, `env_from=[]`. При пропуске профиля/шаблона берутся настроенные значения по умолчанию. При полном доступе пропуск владельца означает `owner_email=null`. У обычного пользователя SAML подставляется email сессии. Cron содержит пять полей. Макросы, секунды, год и встроенный TZ не принимаются. Часовой пояс — IANA, например `Europe/Moscow`, а не `Local`.

[`PATCH`](update-schedule.md) меняет только переданные поля. `null` очищает модель или владельца, `env_from: []` — дополнительные ENV. Менять и очищать владельца может только вызывающий с полным доступом. Пропущенные профиль/шаблон сохраняют текущий выбор, даже если его удалили из Orpheus. Пауза убирает ближайшее время. Возобновление и изменение cron/часового пояса выбирают новое будущее время. Прочие правки сохраняют запланированное время.

[`DELETE`](delete-schedule.md) скрывает задание из списков. Карточка и история сохраняются, в карточке появляется `deleted_at`. Повторное удаление возвращает `204`.

## Повторы

При создании передавайте UUID в [`Idempotency-Key`](create-schedule.md). Повтор с тем же нормализованным телом возвращает исходный ответ, даже если задание позже изменили или удалили. Другое тело с тем же ключом возвращает `409`. Срока истечения у ключей нет. Поля [`url` и `can_edit`](schema-schedule.md) вычисляются по текущему публичному адресу, владельцу и признаку удаления и при повторном ответе. Права создания проверяются до возврата повтора.

Короткий пример с файлом из `examples/space`:

```python
import json
import os
import uuid
from pathlib import Path
from urllib.request import Request, urlopen

key = str(uuid.uuid4())
print("Idempotency-Key:", key)  # Save and reuse after an uncertain response.
request = Request(
    os.environ["ORPHEUS_SPACE_HOST"] + "/api/v1/schedules",
    data=Path("schedule.json").read_bytes(),
    headers={
        "Authorization": "Bearer " + os.environ["ORPHEUS_SPACE_API_KEY"],
        "Content-Type": "application/json",
        "Idempotency-Key": key,
    },
    method="POST",
)
with urlopen(request, timeout=20) as response:
    print(json.load(response)["id"])
```

ENV этого примера совпадает с [CLI](../space.md#cli). Если ответ потерян, используйте сохранённый ключ вместо нового UUID и прежнее тело. Не запускайте пример заново с новым ключом для повтора того же запроса.

## Фильтры и курсоры

[`owner_email`](list-schedules.md) можно повторить до 100 различных адресов. Фильтры объединяются через ИЛИ. Адреса нормализуются: удаляются пробелы по краям, регистр приводится к нижнему. Алиасы почтового провайдера не объединяются. `unowned=true` выбирает только общие задания и несовместим с email-фильтрами.

Список упорядочен от новых заданий к старым. `limit` по умолчанию 50, максимум 200. Передавайте `next_cursor` как `cursor` с теми же фильтрами. В начатый обход не попадают новые задания, но изменения и удаления отражают текущее состояние. [История](list-occurrences.md) также использует курсор.

## Состояние и результат

Список, карточка, история и настройки читаются из Space. Каталоги [профилей](get-profiles.md), [шаблонов](get-templates.md) и [`result`](get-occurrence-result.md) синхронно обращаются к Orpheus. Время получения результата `fetched_at` не заменяет время наблюдения статуса `observed_at` в истории.

Неначавшийся запуск даёт `409`, отсутствующий результат — `404`, недоступный Orpheus — `503`. [Диагностика](../../space/operations.md#diagnostics).

Ошибки имеют вид `error: {code, message, phase, details}`. В `details` путь вроде `["body", "name"]` или `["query", "limit"]` указывает поле. Коды включают `required`, `invalid_type`, `unknown_field`, `invalid_value`. [Схема ошибки](schema-problem.md). Ответы API не кешируются.

## Поля истории {#history}

Срабатывание — запись о наступившем сроке задания. Оно может быть пропущено или не дойти до Orpheus, поэтому ID запуска и его статус допускают `null`. [Полная схема](schema-occurrence.md).

| Поле | Значение |
| --- | --- |
| `id`, `schedule_id` | ID срабатывания и задания |
| `scheduled_at` | Время по расписанию |
| `created_at`, `updated_at` | Создание и последнее изменение записи Space |
| `state` | Отправка: `pending`, `dispatching`, `accepted`, `skipped`, `failed`, `cancelled` |
| `session_id`, `run_id` | ID сессии и запуска, принятого Orpheus |
| `run_status` | Последнее успешно прочитанное состояние выполнения Orpheus |
| `observed_at` | Время успешного наблюдения этого статуса |
| `execution_started_at`, `finished_at` | Фактическое начало и завершение исполнения |
| `error_code` | Ошибка отправки или причина пропуска |
| `run_error_code` | Ошибка выполнения агента |
| `sync_error_code` | Ошибка чтения статуса. Предыдущее наблюдение сохраняется |
| `attempts`, `next_attempt_at` | Число попыток отправки и время следующей попытки отправки или синхронизации |

## Коды ошибок API {#errors}

Основные значения `error.code` в API заданий:

| HTTP | Код | Причина |
| --- | --- | --- |
| 401 | `unauthorized` | Нет действительных учётных данных |
| 403 | `csrf_failed` | Неверный Origin или CSRF-заголовок |
| 403 | `schedule_forbidden` | Сессия не может создать задание на этого владельца или изменить это задание |
| 404 | `schedule_not_found`, `occurrence_not_found`, `not_found` | Задание, срабатывание или маршрут не найдены |
| 404 | `run_result_not_found` | Запись результата не найдена в Orpheus |
| 409 | `run_not_started` | Orpheus ещё не принял запуск |
| 409 | `schedule_busy` | Сброс контекста при активном срабатывании |
| 409 | `schedule_deleted` | Изменение удалённого задания |
| 409 | `idempotency_conflict` | Ключ создания уже использован с другим телом |
| 413 | `request_too_large` | Превышен размер тела |
| 415 | `unsupported_media_type` | Требуется JSON |
| 422 | `validation_error`, `invalid_cursor` | Некорректные поля или курсор |
| 503 | `core_unavailable`, `storage_unavailable` | Недоступны Orpheus или хранилище Space |

Это ошибки HTTP-запроса. Ошибки сохранённого срабатывания, например `previous_run_active`, относятся к полям истории, а не к коду ответа API. [Диагностика](../../space/operations.md#diagnostics).

## Браузерная авторизация {#authentication}

Для браузерной записи нужны точный `Origin`, совпадающий с [`ORPHEUS_PUBLIC_URL`](../space.md#access), и заголовок `X-Orpheus-CSRF: 1`. Space Web отправляет их автоматически. SAML callback вместо этих заголовков проверяет подписанный ответ IdP и начатый в браузере вход. Запросы с валидным Bearer-ключом не требуют этих заголовков. Неверный `Authorization` возвращает `401`, даже если браузерная сессия действительна.

Все авторизованные пользователи могут читать задания и результаты. [Настроенные администраторы](../../space/access.md#permissions) имеют полный доступ. Остальные пользователи SAML создают только на email своей сессии и меняют только свои задания. Явный `null` или чужой владелец при создании дают `403 schedule_forbidden`. Через PATCH нельзя передать, очистить или присвоить владельца. Сессия без email разрешает только просмотр. Bearer-ключи и anonymous сохраняют полный доступ.

[Ответ сессии](schema-authsession.md) содержит `write_access` и `can_manage_all`. У каждого [задания](schema-schedule.md) есть `can_edit`, который после удаления равен false. Эти поля описывают права и не принимаются в запросах записи.
