# Правила и проекты для ревью

Каждый Markdown-файл в корне [`WORKFLOWS_DIR`](../../reference/gitlab-review.md#env-workflows-dir) задаёт workflow. YAML в начале файла выбирает проекты и настройки выполнения. Текст Markdown содержит инструкции для ревью.

## Выберите проекты

```markdown
---
id: backend-review
project_ids: [123, 456]
profile: review
sandbox_template: gitlab-review
services: [gitlab]
language: ru
---

# Правила ревью

Проверь корректность, контроль доступа и изменения публичных контрактов.
Прочитай инструкции проекта и выполни подходящие доступные проверки.
Сообщай об исправимых проблемах этого изменения со ссылками на файлы и строки.
Объясни, какие обязательные проверки не удалось завершить.
```

Замените ID и имена в примере своими. Поле [`services`](../../reference/gitlab-review.md#workflow-services) обязательно. Укажите `services: []`, если шаблон уже предоставляет все необходимые доступы. Сервисы не выбираются неявно.

Поле [`project_ids`](../../reference/gitlab-review.md#workflow-project-ids) задаёт правила для конкретных проектов. Уберите его в одном workflow, чтобы охватить остальные проекты, доступные боту. Явный маршрут имеет приоритет над общим. Проект может входить только в один явный маршрут.

Общий workflow необязателен. Если для назначенного MR нет подходящего workflow, коннектор публикует сообщение о пропуске, снимает только себя с ревью и не запускает агента.

## Запишите правила

Текст Markdown заменяет [инструкции профиля](../../reference/profiles.md#profile-instructions). Включите все необходимые правила ревью: обязательные проверки, источники требований и порядок оценки прежних замечаний. Контекст MR и инструкции по подготовке результатов добавляет коннектор.

Агент анализирует выбранный diff MR в подготовленном репозитории. За публикацию в GitLab отвечает коннектор. Не поручайте агенту публиковать комментарии, одобрять MR или переключаться на новую ревизию ветки.

Поле [`language`](../../reference/gitlab-review.md#workflow-language) задаёт язык текста агента. Оно не переводит сообщения коннектора об успехе, ошибке или пропуске. По умолчанию они на английском.

## Настройте итоговые сообщения

Добавьте [`notes`](../../reference/gitlab-review.md#workflow-notes) в YAML в начале файла:

```yaml
notes:
  success: "✅ Ревью завершено. Подтверждено замечаний: {{ .FindingsCount }}."
  fail: |
    ⚠️ Не удалось завершить ревью: {{ .Reason }}.

    Сессия Orpheus: {{ .SessionURL }}
```

Шаблон заменяет весь видимый комментарий, включая ссылки и эмодзи. Пишите его на нужном языке. Поддерживаются только три [описанных подстановки](../../reference/gitlab-review.md#note-placeholders). Вокруг необязательных значений, например ссылки на сессию, оставляйте осмысленный текст. Сообщение о пропуске проекта без workflow остаётся на английском.

## Примените изменения

После редактирования файлов перезапустите коннектор. В [примере Compose](connect.md):

```sh
docker compose restart review
docker compose logs --tail=100 review
```

Некорректные файлы, повторяющиеся ID, пересечение маршрутов и пустой каталог workflows не дают запуститься всему коннектору. См. [правила проверки](../../reference/gitlab-review.md#validation).

Принятые ревью сохраняют исходные настройки и сообщения, даже если workflow изменён или удалён. Правка файлов не запускает новое ревью. Чтобы применить новые правила, назначьте бота снова после завершения текущей проверки.
