# Пример: обработка тикетов

Цель: по новому тикету подготовить внутренний комментарий для оператора. Агент изучает контекст, предлагает решение и формулирует проект ответа клиенту.

Система хелпдеска в примерах условная. Пути `/tickets/{id}/comments`, поля `body`, `internal` и поддержка `Idempotency-Key` описывают пример контракта. Замените их на контракт своего продукта.

| Решение | Агент публикует сам | Публикует хук |
| --- | --- | --- |
| Токен публикации | Доступен агенту | Передаётся скрипту [`after_run`](../../configuration/hooks.md#hook-after-run) |
| Результат агента | Комментарий через API | Markdown-файл |
| Где задана доставка | В инструкциях и инструменте | В коде публикации |
| Когда удобно | Агенту нужны разные действия в хелпдеске | Формат и момент отправки фиксированы |

В обоих случаях тонкий коннектор получает новое событие, собирает контекст и создаёт сессию. Он не обязан пересылать текст итогового ответа, если публикация уже выполнена агентом или хуком.

Начните с [прямого API-вызова](helpdesk-direct.md) или [Markdown и after_run](helpdesk-hook.md). Для нового сообщения клиента можно создать новую сессию с актуальным контекстом тикета. Если нужен диалог в одной сессии, задайте [`allow_multiple_runs: true`](../../reference/api/create-session.md) при её создании и [продолжайте её](continuation.md), передавая новый контекст.

Отправку сообщения клиенту и изменение статуса добавляйте отдельным явным правилом процесса. В этом примере результат предназначен оператору.
